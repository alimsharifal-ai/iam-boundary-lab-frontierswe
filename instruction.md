# Cloud IAM privilege boundary lab

A fictitious cloud provider inherited an authorization engine that treats matching `Allow` statements as final, even when another policy explicitly denies access. It also incorrectly combines identity permissions and organization guardrails. Implement a replacement policy decision point in `/app/iamlab/engine.py`. Use Python 3.12 and only its standard library. The scenario is fully local and uses synthetic accounts and credentials.

Preserve the two public functions and the `PolicyError` class in the starter. `authorize(request, identity, boundary=None, organization=None, resource=None)` returns exactly `"Allow"` or `"Deny"`. The request contains `action`, `resource`, `principal`, and optional `context` mappings. Each policy is an IAM-like dictionary with a `Statement` object or list of objects. Each statement has `Effect` of `Allow` or `Deny`, and exactly one of `Action` or `NotAction`, and one of `Resource` or `NotResource`. Each action/resource selector accepts a string or list of strings. Wildcards `*` and `?` work as glob patterns. Action matching is case-insensitive; resource matching is case-sensitive. Missing or malformed required fields raise `PolicyError`, never permit access.

An explicit matching Deny from any policy wins. An identity Allow is required, as is an Allow from the resource policy when one is provided. An optional permissions boundary requires its own matching Allow. An optional organization policy requires its own matching Allow. Optional missing layers impose no additional restriction. A policy's unmatched statements imply Deny within that layer. A `NotAction` statement matches when the requested action does not match any listed action pattern. `NotResource` works similarly. A Deny statement with these inverse operators is just as authoritative as any other Deny.

Implement all the following condition operators in `Condition`, as a mapping of operator to mapping of context key to expected string or list of strings: `StringEquals`, `StringNotEquals`, `StringLike`, `StringNotLike`, `Bool`, `Null`, and `IpAddress`. Conditions across operators and keys combine with logical AND. For positive matching, any expected value may match. For negative matching, no expected value may match. Keys absent from the request context fail the comparison except `Null`, which checks whether the key is absent or has a null value. `Bool` accepts case-insensitive strings `true` and `false` or actual booleans. `IpAddress` checks IPv4 or IPv6 values against CIDR networks; invalid address data must not grant access. Match case exactly for condition strings. Condition context keys may include `aws:SourceIp`, `aws:MultiFactorAuthPresent`, and `aws:PrincipalTag/team`.

`authorize_assume_role(request, identity, trust, boundary=None, organization=None)` uses the same evaluator, but it additionally requires a matching Allow from the destination role's `trust` policy. The action must be `sts:AssumeRole` (case-insensitive). The trust policy is evaluated against the request's principal, with its `Principal` or `NotPrincipal` selector (string or list of strings), using case-sensitive glob matching. An explicit Deny in any layer wins. Identity, boundary, organization, and trust must each independently grant access when supplied. There is no real cloud access.

The verifier runs actual permission decisions for legitimate access and attempted escalations, including wildcard grants, inverse deny rules, MFA conditions, source IP restrictions, cross-tenant role trust, and policy layer intersections. The score depends on runtime decisions, not on the format or appearance of submitted code.
